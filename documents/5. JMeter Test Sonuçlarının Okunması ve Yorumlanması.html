Modül 5: JMeter Test Sonuçlarının Okunması ve Yorumlanması

Bu modülde JMeter raporlarını adım adım okuyup, performans problemlerini kaynak sinyalleriyle birlikte yorumlayacaksınız.

İçindekiler / Bölüm Haritası

  • Summary Report ve Aggregate Report
  • Raporlarda Metriklerin Konumu ve Yorumu
  • Grafiklerin Okunması
  • Yavaş Transaction/Endpoint Tespiti
  • CPU/Memory ile İlişkilendirme
  • Database ve Network Problemlerini Ayırma
  • Bottleneck Kavramı
  • Modül Özeti

1) Summary Report ve Aggregate Report Nasıl Okunur?

Summary Report hızlı durum resmi verir; Aggregate Report ise percentile ve istatistikleri daha detaylı okumaya uygundur. İlk değerlendirmede Summary ile genel tabloyu, ardından Aggregate ile dağılımı kontrol edin.

  1. JMeter'da Listener ekleyin: Add → Listener → Summary Report.
  2. Ayrıca Aggregate Report ekleyin.
  3. Test sonrası iki raporu yan yana değerlendirin.
Neden Önemli?
Tek rapora bakmak, sorunun yayılımını kaçırabilir; iki rapor birlikte daha güvenli yorum sağlar.
Dikkat / Sık Yapılan Hata
Çok fazla listener açık bırakmak JMeter tarafında ek yük yaratır.

2) Response Time, Throughput, Error Rate, Percentile Nerede ve Nasıl Yorumlanır?

Aggregate Report içinde ortalama, min, max, 90/95/99 percentile kolonlarını takip edin. Throughput ve error yüzdesi aynı ekranın alt bölümlerinde görünür.

Örnek yorumlama akışı
Adım 1: 95th percentile hedefin altında mı?
Adım 2: Throughput kullanıcı artışıyla büyümüş mü?
Adım 3: Error %1 üstüne çıkmış mı?
Adım 4: En yavaş endpoint hangisi?
Neden Önemli?
KPI odaklı yorum yaparsanız iş birimlerine net, karşılaştırılabilir sonuç sunarsınız.
Dikkat / Sık Yapılan Hata
Status code 200 olsa bile iş sonucu hatalı dönebileceği için assertion sonuçları da kontrol edilmelidir.

3) Grafiklerin Okunması: Response Time, Throughput, Active Users, Error

Grafik okuma sırası önerisi: Active Users ile yük profilini teyit et, Response Time eğrisini izle, Throughput'un plato yaptığı anı bul, Error yükselişini aynı zaman çizgisinde işaretle.

Neden Önemli?
Zaman ekseninde birlikte okuma, kırılma anını yakalayıp kök neden analizini hızlandırır.
Dikkat / Sık Yapılan Hata
Grafikleri farklı zaman diliminde okumak yanlış ilişki kurdurur.

4) Performans Problemlerinin Belirlenmesi

Önce en yüksek gecikmeye sahip transaction/endpoint'i bulun, ardından hata artışının aynı endpoint'te mi yoksa farklı bir çağrıda mı olduğunu kontrol edin.

  1. Aggregate Report'ta en yüksek 95th değere sahip satırları sıralayın.
  2. Error yüzdesi artan endpoint'leri listeleyin.
  3. Bu endpoint'ler için log ve APM ekranlarını açın.
Neden Önemli?
Genel ortalama yerine işlem bazlı hedefleme, iyileştirme maliyetini düşürür.
Dikkat / Sık Yapılan Hata
Tüm sistemi optimize etmeye çalışmak yerine problemli 1-2 kritik akışa odaklanılmalıdır.

5) CPU/Memory Kullanımı ile Sonuçları İlişkilendirme

Response time artışıyla aynı dakika içinde CPU %90+ veya memory sürekli yükseliyorsa uygulama katmanında baskı olabilir. Memory artışı test sonuna kadar geri düşmüyorsa sızıntı adaydır.

Örnek bulgu
11:20 sonrası response time artıyor
CPU: %65 -> %92
Memory: 7.2 GB -> 9.8 GB
Yorum: Uygulama katmanında işlem yoğunluğu ve olası memory baskısı
Neden Önemli?
Kaynak sinyali olmadan yalnız JMeter verisiyle kök neden çıkarmak risklidir.
Dikkat / Sık Yapılan Hata
OS seviyesinde ortalama CPU'ya bakıp process bazlı tüketimi incelememek.

6) Database ve Network Kaynaklı Problemleri Ayırt Etme

DB kaynaklı sorunlarda query süresi, lock bekleme ve connection pool doluluğu yükselir. Network kaynaklı sorunlarda timeout, yeniden deneme ve dalgalı gecikme deseni öne çıkar.

Ayırt etme kontrol listesi
- DB pool %100 mü?
- Uzun çalışan sorgu arttı mı?
- Ağ gecikmesi aynı anda sıçradı mı?
- Paket kaybı/yeniden deneme var mı?
Neden Önemli?
Yanlış ekipte çözüm aramak, olay çözüm süresini uzatır.
Dikkat / Sık Yapılan Hata
Her yavaşlıkta veritabanını suçlamak; bazen dış servis veya ağ katmanı temel etkendir.

7) Bottleneck Kavramı ve Somut Örnek

Bottleneck, sistemin toplam kapasitesini sınırlayan en dar noktadır. Örneğin API katmanı saniyede 400 istek işleyebilse de DB bağlantı havuzu 120 bağlantı ile sınırlıysa kapasite bu noktada sıkışır.

ERP örneği: Stok sorguları hızla artarken cache dışı kalan sorgular DB'yi kilitliyor, response time ve error rate aynı anda artıyor. Burada darboğaz DB katmanıdır.

Neden Önemli?
Doğru darboğaz tespiti, doğru yatırım kararını sağlar.
Dikkat / Sık Yapılan Hata
Darboğazı görmeden sadece sunucu sayısını artırmak maliyeti yükseltir ama sorunu çözmeyebilir.

Modül Özeti

  • CPU/memory/DB/network metrikleriyle korelasyon
  • Bottleneck kavramının kurumsal örneklerle uygulanması
